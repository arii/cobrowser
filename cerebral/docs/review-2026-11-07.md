## Claims and fixes

### 1. verify() covers only the record chain; receipt.success, goal_verdicts and identity fields are unhashed

**Claim.** A receipt whose success flag, goal verdicts, run_id, skill_id, skill_version and per-record timestamps have all been rewritten still passes verify() with the original final_link, because none of those fields enter any hash.

**Scenario.** Take a run that handed off (records=[handed_off], success=False). Set receipt.success=True, replace goal_verdicts with a fabricated passed verdict, change skill_version/skill_id/run_id and every record's `at`. verify() returns (True, []) and final_link is unchanged, so POST /receipts/verify and the uAgent ReceiptAnnounce (which publishes final_link next to success) vouch for a forged outcome. An empty receipt with records=[] and any arbitrary final_link also verifies, since the final_link check is guarded by `if receipt.records`.

**Fix.** Add a receipt-level seal: hash (run_id, skill_id, skill_version, genesis, last record link, goal_verdicts, success) into final_link (or a separate `receipt_link`) and have verify() recompute it; stop excluding `at` from record_link, or document that timestamps are unattested. Reject an empty receipt whose final_link != genesis.

### 2. Correction endpoint rewrites a sealed record and the receipt never records what the human did

**Claim.** After handoff the API mutates the already-sealed last StepRecord (human_corrected=True), reseals it and replaces final_link; the human's trace is never appended to the chain, and finish() then counts that record as success even though its sealed evidence (post_hash, post_verdicts) is the failed state.

**Scenario.** GET /runs/{id}/receipt while awaiting_human returns receipt A (final f2545afa..., record0 human_corrected=False). POST /correction produces receipt B with the same record count, record0 human_corrected=True, a different link/final_link. Both A and B verify; a holder of A cannot distinguish 'the record was edited after sealing' from 'it was always so', which is exactly what the DESIGN forbids (section 6: 'Nothing in the chain is rewritten'). The resumed run then finishes with status succeeded and receipt.success=True while record0 still shows outcome=handed_off, post_verdicts=['failed'] and post_hash=hash(home): the receipt proves a failure and claims success, with no record of the state transition the human produced (body.trace is only persisted into skill.history).

**Fix.** Never mutate a sealed record. Append a new StepRecord of outcome human_corrected (or a dedicated correction record) carrying pre_hash=hash(trace[0].before), the human's action(s), post_hash=hash(trace[-1].after), and verdicts re-checked against the corrected postconditions; only then let finish() count the step as satisfied.

### 3. Correction accepts any step_id, so receipt and skill history can name different steps

**Claim.** The correction endpoint never checks that body.step_id is the step of the handed-off record (or that the last record is actually handed_off), so a correction for an unrelated step is merged into the skill while the handed-off record is still marked human_corrected.

**Scenario.** Run hands off on step 0. POST /correction with step_id of step 1 and a new_action returns 200: step 1's action is replaced, skill.history[-1].step_id is step 1, but receipt.records[-1] (step 0) is flagged human_corrected and the run resumes at step 1 with the step-0 failure 'fixed' by nothing. The receipt, the skill diff and the ledger's interventions count now describe three different things.

**Fix.** Require `body.step_id == run.receipt.records[-1].step_id` and `records[-1].outcome == handed_off`; return 409 otherwise.

### 4. Repaired step record has a stale pre_hash and omits the failed attempt

**Claim.** seal() always uses the pre_snapshot captured by precheck, but after a repair the recorded action was executed from the post-state of the failed attempt, so the sealed (pre_hash, action, post_hash) triple describes a transition that never happened, and the failed attempt's action, intermediate state and failed verdicts appear nowhere in the chain.

**Scenario.** precheck sees home; click lands on /search (url_matches fails); policy says retry; second click lands on /p/42 and passes. The single sealed record says pre=hash(home), action=click, post=hash(product), outcome=repaired, repairs=1, post_verdicts=[passed]. hash(/search) and the failed verdict are absent, contradicting DESIGN rule 3 ('Every pass through postcheck appends one sealed record... including failures'). A verifier replaying from stored snapshots would find the record's pre-state does not precede its action.

**Fix.** Seal a record (outcome failed, repairs=attempt) on every postcheck failure before entering repair, and set pre_snapshot = post_snapshot of the failed attempt so the retry's record is a genuine transition.

### 5. Ledger charges the intervention to the new skill version; run and receipt disagree on skill_version

**Claim.** The correction bumps run.skill_version to the post-fix version but leaves receipt.skill_version at the version that actually ran, and the ledger entry copies run.skill_version, so the intervention that created version N+1 is recorded against version N+1.

**Scenario.** Skill v1 runs, hands off (interventions=1), human corrects (skill becomes v2), run resumes and succeeds. Ledger entry: skill_version=2, interventions=1, success=True; receipt.skill_version=1. trends() keys its series on e.skill_version, so the headline 'interventions fall to zero across versions' chart shows v2 with 1 intervention and v1 with none, the inverse of what happened.

**Fix.** Keep run.skill_version as the version the run started with (or derive the ledger entry from receipt.skill_version), and record the corrected-to version in a separate field if the dashboard needs it.

### 6. snapshot_hash collapses quantities, totals, IDs, repeated elements and all widget state

**Claim.** Digit masking plus set-deduplication of (role, name) pairs, while ignoring A11yNode.value, title, text and network, makes the pre/post hashes blind to most of the state a shopping or form task actually changes, so a receipt can show identical before/after hashes for materially different pages (or different outcomes for the same page).

**Scenario.** All of these hash identically: cart 'Widget x 1' vs 'Widget x 3'; 'Total $0.00' vs 'Total $999.99'; one 'Remove' button vs three; 'Step 1 of 3' vs 'Step 3 of 3'; 'Order #1234' vs 'Order #9876'; a checked vs unchecked 'Agree' checkbox (value ignored on the Python side, and snapshot.ts always emits value:'' and strips the `[checked]`/`[expanded]`/`[disabled]` suffix); a page whose POST /api/pay returned 500 vs 200. Conversely masking depends on spacing: 'Qty x 3' == 'Qty x 5' but 'Qty x3' != 'Qty x5' because `\b\d` needs a word boundary. An empty tree from a failed ariaSnapshot() (`.catch(() => "")`) hashes exactly like a genuinely empty page, so a capture failure is indistinguishable in the receipt.

**Fix.** Hash a multiset (keep duplicates), include role state (checked/expanded/selected, value for non-free-text widgets) from the aria snapshot, and consider hashing a digit-preserving variant of names that look like quantities/totals; flag an empty-tree capture explicitly rather than hashing it as a page.

### 7. snapshot.ts a11y parser drops text nodes, truncates names with escaped quotes, and strips state

**Claim.** The line regex only accepts a double-quoted name, so aria-snapshot lines of the form `- text: ...` / `- paragraph: ...` yield name='' and are discarded, names containing `\"` are cut at the backslash, and `[checked]`/`[level=N]`/`[disabled]` suffixes are ignored; the Python hash therefore sees a thinner, sometimes wrong tree than the page has.

**Scenario.** A button labelled `Say "hi"` is recorded as role=button name='Say \' (and the recorder-derived anchor `name=Say "hi"` will never match element_visible). A status banner rendered as plain text (`- text: Payment accepted`) never enters tree, so the pre/post hash cannot change when the only visible effect of a step is new text. Toggling any checkbox or expanding any disclosure leaves the hashed tree identical.

**Fix.** Parse the YAML properly (or use Playwright's structured accessibility snapshot), keep `: text` content as the name for text/paragraph roles, unescape quotes, and carry `[state]` into A11yNode.value.

### 8. handoff() never updates run.current_step, so a second handoff on a resumed run resumes at the wrong step

**Claim.** Only advance() writes run.current_step; handoff() leaves it at the last advanced value, so when the first step of a resumed segment hands off, api.correction's start_step = run.current_step + 1 points at the step the human just performed instead of the one after it.

**Scenario.** 2-step skill. Step 0 fails -> handoff (current_step=0). Correction resumes at 1. Step 1 fails -> handoff, but current_step is still 0 (record index 1 sealed). Second correction computes start_step = 0 + 1 = 1 and re-runs step 1 (clicking 'Add to cart' again after the human already did it), appending a second StepRecord with index 1. Receipt ends with indices [0, 1, 1], receipt.verify() still returns (True, []) because it does not check index monotonicity, and finish() marks the run succeeded. Same shape for a 3-step skill when step 1 passes and step 2 is handed off twice.

**Fix.** In handoff() set run.current_step = state['step_index'] before sealing (or have run_skill set run.current_step = start_step on entry and every node keep it equal to step_index). Optionally derive the resume index in api.correction from run.receipt.records[-1].index + 1 instead of run.current_step, and have receipt.verify() reject non-increasing record indices.

### 9. Concurrent corrections both pass the awaiting_human check and spawn two resumed runs on the same run id

**Claim.** correction() reads the run from disk, checks status, mutates the skill and receipt, then awaits driver.set_control before store.save_run; two overlapping POSTs both observe awaiting_human, both bump the skill version and append history, and both create a _drive task that drives the same run and writes the same run file.

**Scenario.** Canvas double-submits (or two operators click Done) while the run is awaiting_human. Both requests return 200; skill version goes 1 -> 3 with two history entries for one fix; two graph loops run concurrently against the same browser session, each appending records to its own in-memory copy of the receipt and overwriting runs/<id>.json, and ledger.record(run) is called twice.

**Fix.** Guard the check-and-transition with a per-run asyncio.Lock (or persist status=running and save_run before any await), and refuse a correction while _tasks[run.id] is still not done.

### 10. wait_then_retry re-performs the step's action instead of re-checking, so non-idempotent actions execute twice

**Claim.** The only path out of repair() is back into act(); the deterministic policy picks wait_then_retry for failed element_visible/text_present ("target likely still loading"), so a click whose postcondition merely has not rendered yet is clicked again after the wait.

**Scenario.** Step 'add to cart' clicks the button; the cart text has not appeared when the post-snapshot is taken. repair() waits 1.5s and the graph goes repair -> act, clicking 'Add to cart' a second time; the cart now has 2 items but the receipt records the step as 'repaired' and goal checks like text_present 'Widget x 1' may fail or, worse, pass on a different quantity. Same for form submits and payments.

**Fix.** Add a repair -> postcheck edge for wait_then_retry (re-snapshot via driver.snapshot and re-run postcheck without acting), and reserve repair -> act for retry/re_anchor.

### 11. Task cancellation escapes _drive's except Exception, leaving the run 'running' on disk forever

**Claim.** _drive only catches Exception; asyncio.CancelledError (BaseException) raised when the server shuts down or the task is cancelled skips the failure bookkeeping, so the persisted run stays status=running with no finished_at and no ledger entry.

**Scenario.** uvicorn reloads or is stopped while a run is mid-step. On restart GET /runs shows the run as running indefinitely, POST /runs/{id}/correction returns 409 (not awaiting_human), and the ledger never records it; the dashboard's per-skill series silently omits the run.

**Fix.** Use try/finally (or also catch asyncio.CancelledError) to persist a terminal status, and on startup mark any run file still 'running' as failed/abandoned.

### 12. correction() does not check that step_id is the handed-off step, but still marks the last record human_corrected and skips it

**Claim.** body.step_id is matched against any step in the skill, while the human_corrected flag is unconditionally applied to receipt.records[-1] and the run resumes at current_step + 1; a correction for a different step edits that step, falsely certifies the handed-off record as corrected, and skips the step that actually failed.

**Scenario.** Run handed off on step 0 ('s0'). Canvas sends a correction with step_id of step 1 (stale selection). Response 200: step 1's action is overwritten, record 0 (s0) is resealed with human_corrected=True, and the run resumes at step 1 having never fixed s0. finish() then counts record 0 as ok and the run can end succeeded.

**Fix.** Require body.step_id == run.receipt.records[-1].step_id (409/400 otherwise), or drop step_id from the body and take the step from the handed-off record.

### 13. Meta fallback judge does not fail closed: exceptions propagate and low-confidence 'holds' passes

**Claim.** MetaClient.judge has no try/except and applies no confidence threshold, so a transport error or malformed model reply crashes the run node and a 'holds: true' with confidence 0.05 counts as a passed semantic assertion.

**Scenario.** META_API_KEY set, SUBQ_API_KEY unset. (a) Llama endpoint returns 502, or returns non-JSON, a JSON list, or {"holds": true, "confidence": "high"} -> RuntimeError / JSONDecodeError / AttributeError / ValueError escape check_all, the precheck/postcheck/finish graph node raises, _drive marks the run failed with no sealed record for the step. (b) Reply {"holds": true, "confidence": 0.05, "reason": "guess"} -> judge returns (True, 0.05, ...) and the goal check passes, whereas SubqJudge would fail anything under 0.7.

**Fix.** Wrap _chat/json.loads/field coercion in try/except returning (False, 0.0, f"meta unavailable: {type(e).__name__}"); require isinstance(d, dict); gate on confidence >= JUDGE_THRESHOLD (import from subq or share a constant) so holds only passes with confidence above threshold.

### 14. Non-required network_ok failure flips the repair policy from wait_then_retry to immediate handoff

**Claim.** _policy builds the failed-kind set from every verdict regardless of Assertion.required, so the derived non-required network_ok assertion (which fails whenever the matching response is absent or non-2xx in the drained window) pushes the set outside {element_visible, text_present} and the policy hands off instead of waiting and retrying.

**Scenario.** Step postconditions: element_visible 'role=heading name=Your cart' (required) and the derived network_ok '/g/collect' (required=False). On replay the heading is still rendering and the analytics beacon has not fired -> verdicts [element_visible failed, network_ok failed]. graph.repair -> decide_repair (no Subq key) -> _policy: failed = {'element_visible','network_ok'}; not a subset of the retry kinds and no url_matches -> strategy='handoff' with rationale "unhandled failure kinds: ['element_visible', 'network_ok']". Without the non-required verdict the same state yields wait_then_retry. Every such step costs a human intervention and the bounded-repair path never runs.

**Fix.** Pass the step (or the set of required assertion ids) into _policy/_state and consider only failed verdicts whose assertion is required; alternatively filter verdicts in graph.repair before calling decide_repair.

### 15. network_ok counts redirect and unrelated prefix-matching responses, so a successful POST that redirects fails

**Claim.** network_ok treats every response whose URL contains the expected substring as a hit and requires all of them to be 2xx, so a normal POST -> 302 -> GET 200 flow, or any unrelated request sharing the path prefix, fails the assertion.

**Scenario.** Expected '/cart' (derived from a POST). Post-action snapshot network: [POST https://shop.test/cart 302, GET https://shop.test/cart 200] -> hits = both, all(2xx) is False -> failed with evidence '2 matching responses'. Derived expected '/' (POST to the site root) matches every URL, so one unrelated 500 from /recs fails it. Combined with the policy finding above this forces handoffs.

**Fix.** Match on urlsplit(e.url).path == exp (or startswith for a path prefix), ignore 3xx or pass if any matching response is 2xx; have derive store method+path and compare method too.

### 16. _url_pattern does not regex-escape the path, so derived url_matches can never match URLs with regex metacharacters

**Claim.** Only scheme+netloc are re.escape'd; the path is substituted into the regex raw, so '(', '+', '[', '.', '|', '$' in the path change or break the pattern and the derived precondition/postcondition fails or raises on replay of the exact same URL.

**Scenario.** Demo lands on https://shop.test/c/(all)/items -> pattern '^https://shop\.test/c/(all)/items' does not match that URL (parens are a group). https://shop.test/s/a+b -> '/s/a+b' never matches 'a+b'. https://shop.test/search/[q] -> re.search raises re.error inside check_deterministic, crashing the postcheck node. As a postcondition this is required, so the step fails on every replay and ends in handoff.

**Fix.** re.escape each path segment first, then replace escaped all-digit segments: '/'.join(r'\d+' if seg.isdigit() else re.escape(seg) for seg in p.path.split('/')); optionally catch re.error in check_deterministic and return a failed verdict.

### 17. Derived url_matches freezes per-session identifiers that are not pure digits

**Claim.** The volatile-segment replacement only handles segments that begin with digits, so alphanumeric or prefixed ids (order numbers, hex session/cart ids, slug-id) are baked into the required url_matches postcondition and the skill can never pass that step on another run.

**Scenario.** Demo click 'Checkout' navigates to https://shop.test/checkout/ORD-9/x or https://shop.test/cart/3f9a2b. Derived postcondition expected '^https://shop\.test/checkout/ORD-9/x'. Next run lands on /checkout/ORD-10/x -> required url_matches fails -> retry -> handoff every time.

**Fix.** Treat any segment containing a digit (or matching receipt._VOLATILE / a hex/uuid pattern) as volatile and emit '[^/]+' for it; or anchor only on the static path prefix up to the first volatile segment.

### 18. Derived element_visible postconditions encode volatile text that the diff itself normalized away

**Claim.** _new_nodes compares (role, normalize_name(name)) but the emitted assertion uses the raw n.name, and element_visible compares against raw snapshot names, so a newly appeared node whose label contains a timestamp, count or price becomes a required postcondition that fails on any replay where the number differs.

**Scenario.** Add-to-cart demo: after-tree gains ('status', 'Added 10:42'). Derived required postcondition 'role=status name=Added 10:42'. Replay at 11:07 shows ('status', 'Added 11:07') -> element_visible False -> step fails -> handoff. Same for 'Order #48213 placed', 'Subtotal $9.99', '3 items'.

**Fix.** Either store the normalized name and normalize snapshot names in element_visible (compare normalize_name(n.name)), or skip nodes whose normalized name differs from the raw lowercased name (i.e. contain volatile tokens) when deriving.

### 19. Steps that change no (role, name) node and no path derive zero postconditions and always pass

**Claim.** derive_postconditions ignores A11yNode.value and query-string changes, so a 'type' or 'select' step (and clicks like toggling a checkbox) usually yields an empty postcondition list, and all_required_passed([], []) is True, so the step is recorded as passed even when the action silently failed.

**Scenario.** Demo: type 'widget' into role=textbox name=Search. before.tree == after.tree in (role, name) terms, path unchanged, no non-GET 2xx -> postconditions = []. On replay the fill times out or targets a different textbox; the worker still returns a snapshot, check_all([]) -> [], all_required_passed -> True, StepOutcome.passed is sealed into the receipt. The next step's precondition failures are 'recorded, not blocking' (graph.py:126), so nothing ever catches it.

**Fix.** For type/select actions derive a deterministic check on the field value (add value-aware A11yNode comparison or a text_present on action.value), and treat a step with no postconditions as needing a semantic/judge check or a handoff rather than a silent pass.

### 20. Empty or anchor-less expected strings make deterministic assertions trivially true

**Claim.** Assertion.expected has no validation, so expected='' passes text_present and url_matches unconditionally, and an element_visible expected without 'role='/'name=' tokens (e.g. a bare label from a human correction) passes on any non-empty tree.

**Scenario.** POST /runs/{id}/correction with new_postconditions [{kind: text_present, expected: ''}] or [{kind: element_visible, expected: 'Add to cart'}] on an error page whose tree is [('heading','Oops 404')] -> both verdicts passed, step and run marked successful.

**Fix.** Validate Assertion.expected (min_length=1; for element_visible require parse_anchor to yield role or name, else fail the verdict with evidence 'unparseable anchor').

### 21. parse_anchor lets a 'key=' token inside the element name override role (and diverges from the worker's locator)

**Claim.** The findall regex treats any whitespace-separated word followed by '=' inside the name as a new key, so a name containing ' role=...' overwrites the role and the assertion can never pass, while session.ts takes the first role= match, so verifier and worker disagree on the same anchor.

**Scenario.** Recorder emits 'role=button name=Switch role=admin' for a button labelled 'Switch role=admin'. parse_anchor -> {'role': 'admin', 'name': 'switch'}; element_visible on a tree containing ('button', 'Switch role=admin') returns False -> derived precondition/postcondition fails every run. session.ts locate() would use role=button.

**Fix.** Parse only the known keys: role = first r'\brole=(\w+)'; name = everything after the first 'name=' to end of string (matching session.ts), or encode the anchor as JSON/structured fields instead of a string.

### 22. decide_repair crashes the repair node when Subq returns an out-of-vocabulary strategy

**Claim.** Only the HTTP call is wrapped in try/except; if the probabilities dict contains a key outside the Strategy literal and it has the max probability, constructing RepairDecision raises a pydantic ValidationError that escapes decide_repair and aborts the run.

**Scenario.** Subq answers {"strategy": {"probabilities": {"retry": 0.1, "escalate": 0.9}}} -> best='escalate' -> RepairDecision(strategy='escalate') raises ValidationError in graph.repair; _drive marks the whole run failed with no handoff and no sealed record for the step, contradicting the 'never let the sponsor call block the loop' comment.

**Fix.** Filter probs to the four known strategies before taking max (fall back to _policy if empty), or wrap the RepairDecision construction in the same except path.

### 23. /act masks every failure (including the human-has-control refusal) as HTTP 200 + snapshot, so the Python run loop cannot tell a performed action from a refused one

**Claim.** server.ts catches any error from Session.act, including `human has control` (session.ts:74), and returns `reply.code(200); return s.snapshot()`; browser_client.HttpDriver only detects failure via raise_for_status, and graph.act stores whatever comes back as post_snapshot, so a refused action is indistinguishable from an executed one.

**Scenario.** A run is `running`. The human clicks 'Take over' (RunView.tsx:37-40 -> POST /control who=human, which also starts the recorder). The agent's next driver.act() (graph.py:49) hits session.ts:74 `throw new Error('human has control')`; server.ts:41 skips actNatural because control !== 'agent', returns 200 with the current snapshot. graph.postcheck evaluates postconditions against a page the agent never touched: for a `wait`/`noop` step or any step whose postconditions already hold, the step is sealed `passed` in the receipt although nothing was done; otherwise it burns the repair budget and hands off while the human is already driving. The receipt records a pre/post hash pair for an action that did not happen.

**Fix.** Return a non-2xx (409) when control is 'human' and a 4xx/5xx or an explicit `{performed: false, error, snapshot}` envelope when the locator fails without a Stagehand fallback; have HttpDriver surface that so graph can route straight to handoff or mark the record `failed` instead of sealing a fabricated action.

### 24. Web 'Take over' + 'Hand back' posts a correction while the run is still `running`; the API answers 409 and the UI leaves the session stuck with the human holding control

**Claim.** api.py only accepts /runs/{id}/correction when run.status == awaiting_human (409 otherwise), but RunView lets the human take control at any time and handBack has no error handling, so the 409 is an unhandled rejection and the worker's control is never returned to 'agent'.

**Scenario.** Status is `running`; human clicks 'Take over' (POST /control who=human, recorder starts), fixes something, clicks 'Hand back to agent'. handBack calls recordStop (recorder drained, events returned) then POST /runs/{id}/correction -> api.py:143-144 raises HTTPException(409, 'run is not awaiting a human'). j() throws (api.ts:37); handBack has no try/catch, so the error is swallowed as an unhandled promise rejection, `setHuman(false)` on line 54 never runs, and api.py:177 `driver.set_control(session_id, 'agent')` never executes. The worker stays in control='human', every later /act from the agent is refused and masked as 200 (see the /act finding), and the human sees no error.

**Fix.** Either hide 'Take over' unless status is awaiting_human, or add an API route that lets the human preempt a running run (set status awaiting_human, cancel the _tasks entry) before accepting the correction. In all cases wrap handBack in try/catch, surface e.message, and on failure call api.setControl(sessionId, 'agent') or leave the human-mode UI visible with an explanation.

### 25. RunView free-text postconditions map straight onto Assertion.kind; any line that is not an exact enum value yields a 422 that the UI never shows

**Claim.** handBack turns each textarea line into `{kind: <text before first colon>, expected, source: 'human', required: true}`; Python Assertion.kind is the AssertionKind enum (url_matches | element_visible | text_present | network_ok | semantic), so any spelling variant, spaces, or a line without a colon fails Pydantic validation with 422, and handBack has no catch.

**Scenario.** Human enters `text present: Your cart` (space instead of underscore) or just `Your cart`. The web sends `{kind: 'text present', expected: 'Your cart', ...}` or `{kind: 'Your cart', expected: '', ...}`; FastAPI returns 422 (reproduced locally: Assertion.model_validate raises ValidationError on both). j() throws, nothing catches it, the form stays open with no message, and the correction (including the recorded trace) is not applied. The run stays awaiting_human indefinitely.

**Fix.** Validate `kind` on the client against the five enum strings (a <select> per line, or a shared const mirrored from AssertionKind) and show the error text from the 422 body in the existing `err` pattern used by DemoRecorder/RunLauncher.

### 26. Recorded opening navigate uses an about:blank `before`, so derive_preconditions gives step 1 a `url_matches ^about://blank` precondition that fails on every replay

**Claim.** /record/start with `url` runs recorder.perform(navigate), whose start() snapshots the current page (about:blank) as `before`; the Python derive step turns that into a url_matches precondition on step 1, but RunLauncher opens the run session already navigated to the site, so the precondition can never pass.

**Scenario.** Demonstrate any skill via DemoRecorder (always passes `url`). skills/<id>.json step 1 gets `preconditions: [{kind: url_matches, expected: '^about://blank'}, ...]` (reproduced: _url_pattern('about:blank') -> '^about://blank', no match against 'https://shop.example.com/'). On every run, RunLauncher.tsx:14 opens the session at the site, graph.precheck records a failed pre_verdict for step 1. Precondition failures are non-blocking (graph.py:126), but the failed verdict is counted in LedgerEntry.assertions_total/assertions_passed (ledger.py:12-21), so the dashboard pass_rate for every skill is permanently capped below 100% and the receipt for every run shows a red precondition on step 1.

**Fix.** In derive_preconditions skip url_matches when ev.before.url is about:blank (or the step is a navigate), or in server.ts /record/start navigate first and then start the recorder so `before` is the real landing page; alternatively have RunLauncher open the session without a url and let step 1's navigate do it.

### 27. Take over does not stop the running graph; hand-back is rejected and refused actions are sealed as performed

**Claim.** The Take over button only flips the worker's control flag; the Python _drive task keeps looping, /act silently returns a snapshot when refused, the graph seals those steps as if the agent performed them, and POST /runs/{id}/correction returns 409 because the run is still 'running'.

**Scenario.** Run is 'running' at step k. Human clicks Take over -> POST /control human (worker only). Graph calls /act: Session.act throws 'human has control' (session.ts:74); server.ts:41 skips the natural fallback (control !== 'agent') and returns 200 + snapshot (server.ts:44-45), so graph.py act() cannot tell the action was refused. postcheck fails -> _policy wait_then_retry (subq.py:96-97) -> loops until max_repairs. If the human finishes step k on the canvas meanwhile, postcheck passes and seal() writes a StepRecord with action=s.action, outcome=passed, human_corrected=False and interventions unchanged (graph.py:69-80), i.e. the receipt attests to an action that never ran and the ledger undercounts the intervention. The agent then 'advances' and the same happens for step k+1... until it finally hands off on some later step m. Meanwhile the human clicks 'Hand back to agent': recordStop succeeds, then api.correction -> api.py:143 raises 409 'run is not awaiting a human'; the rejection is unhandled, setHuman(false) never runs, no error is shown, and the panel stays stuck. When the graph eventually hands off at step m, the accumulated trace (the fix for step k) is merged into step m.

**Fix.** Make takeover a first-class API operation: POST /runs/{id}/takeover that cancels _tasks[run.id] (or sets a cooperative stop flag the graph checks between nodes), seals the current step as handed_off, increments interventions, sets status awaiting_human and then calls driver.set_control(human). Have /act return a non-200 (e.g. 409) when control is human so the graph halts instead of postchecking a snapshot it did not produce. Surface errors from handBack in the UI.

### 28. Empty session id from sessionStorage spawns a new Chromium for id "" and resumes the run on a blank page

**Claim.** RunView falls back to sessionId "" when sessionStorage has no entry, yet still offers Take over and Hand back; both forward "" to the worker, whose get() lazily creates a Session for any id, so a brand-new browser is launched and the run resumes against about:blank while the real session stays locked on human.

**Scenario.** The run was launched in tab A (RunLauncher.tsx:16 writes `session:<runId>` to sessionStorage, which is per tab). The user opens /runs/<id> in a new tab from the skill page or the eval table (app/skills/[id]/page.tsx:39, app/eval/page.tsx:28), or reloads after closing the tab. sessionId becomes "" (RunView.tsx:19). When the run reaches awaiting_human the hand-back panel still renders (RunView.tsx:72) even though line 69 says no session is attached. Clicking Hand back skips recordStop (guarded on line 52) but calls api.correction with session_id "" (line 53). api.py:177 calls driver.set_control("", "agent") -> server.ts:16-23 get("") creates `new Session("")` and launches Chromium; api.py:179 resumes _drive against session "" so every subsequent step runs on a blank page and fails. The original session keeps control=human with its recorder running. Take over (line 38) with sessionId "" has the same effect while the run is still running.

**Fix.** Store session_id on the Run (RunStart already receives it) and have /correction use run.session_id instead of trusting the body; in RunView disable Take over / Hand back when sessionId is empty (or read it from the Run). In the worker, have /control, /act, /ws reject unknown session ids instead of lazily launching a browser; only /sessions should create one.

### 29. Canvas sends mouseMoved with button "left", so every hover is a left-button drag in the page

**Claim.** All forwarded mouse events, including mouseMoved, carry button: "left"; for Input.dispatchMouseEvent that means the left button is held during the move, which Chrome turns into drag/selection, not a plain hover.

**Scenario.** Human has control and simply moves the pointer across the canvas. Each onMouseMove sends `{type:"mouseMoved", x, y, button:"left", clickCount:0}`. Chrome dispatches mousemove with the left button pressed (this is exactly how Puppeteer/Playwright implement drags: mouseMoved with button 'left'), so pages see e.buttons===1 during hover: text gets selected while moving between fields, draggable elements and sliders start dragging, hover menus that check for no-button-down do not open, and a subsequent mousePressed/mouseReleased pair may land as the end of a drag rather than a click. Because the move has no `buttons` bitfield either, Chrome falls back to deriving button state from `button`.

**Fix.** Track pressed state in the canvas: send button: "none" (and buttons: 0) for mouseMoved unless a button is held, and only send button: "left"/buttons: 1 while dragging. Also forward e.detail as clickCount so double-clicks work, and forward modifiers.

### 30. Control is checked once at the start of act(); an in-flight Playwright action lands under human control and is recorded as the human's fix

**Claim.** Session.act and actNatural check `control` only on entry; a click/fill with an 8 s actionability wait, a navigate, a `wait` action, or a multi-second Stagehand act() continues after /control human is processed, and because /control human starts the Recorder immediately, the agent's DOM-level click/input is captured as a human trace event.

**Scenario.** Graph calls /act click on an element that is not yet visible; locator.click({timeout: 8000}) waits. Human clicks Take over (or the graph's own handoff arrives for a different in-flight request after a repair): server.ts:55-60 sets control=human and calls recorder.start(), which sets active=true. The element appears, Playwright dispatches real mouse events, the injected PAGE_SCRIPT (recorder.ts:88-92) fires the binding and enqueue() records {kind:'click', target:...} because active is true. act() returns normally (no throw), so server.ts returns the snapshot and the graph keeps going as if it still drove. Later the human hands back; api.py:152-153 takes trace[-1].action, which may be the agent's click, as the 'human' correction and derives postconditions from it. actNatural (session.ts:111-113) has the same single check before a long LLM-driven action.

**Fix.** Keep an in-flight promise/abort token per session: setControl('human') should await (or cancel via a short timeout) the current act before returning, and act() should re-check control after the action completes and report 'refused/raced' to the API. Pause the recorder (or tag events with the controller at the moment they fire) while an agent action is outstanding.

### 31. Page.screencastFrame handler is registered on every 0->1 listener transition and never removed

**Claim.** startScreencast calls cdp.on(...) each time the listener set grows from 0 to 1 but the returned stop() only deletes the listener and stops the screencast; the CDP handler is never detached, so handlers accumulate across canvas reconnects.

**Scenario.** Canvas connects (handler #1 registered), disconnects (size 0, stopScreencast sent, handler #1 stays), reconnects (size 1 again, handler #2 registered, startScreencast). Now every Page.screencastFrame invokes both handlers: each socket receives every frame twice and Page.screencastFrameAck is sent twice per frame. In Next dev, React StrictMode mounts CoBrowseCanvas twice, so this happens on the very first page load; each page reload or tab switch adds another handler. After N reconnects the canvas receives N copies of each frame (N x bandwidth and N re-renders per frame) for the life of the session.

**Fix.** Register the Page.screencastFrame handler once in start() (fan out to the current listener set), and let startScreencast/stop only toggle Page.startScreencast/stopScreencast; or store the handler and call this.cdp.off(...) in stop() when the set empties.

### 32. WebSocket close listener is attached after two awaits, so a client that disconnects during setup leaks the screencast and trace listeners permanently

**Claim.** The /ws/:id handler awaits get(id) (which may launch Chromium) and startScreencast before calling socket.on("close"); a close that happens during those awaits is never observed, so stop()/offTrace() never run.

**Scenario.** CoBrowseCanvas opens the socket; React StrictMode (dev) immediately runs the effect cleanup, sock.close(), and reopens. Or the user navigates away while the worker is still in get(id) launching Chromium (seconds). The 'close' event fires before line 124 registers its listener, so the frame listener stays in screencastListeners and the trace listener stays in recorder.listeners for the lifetime of the Session. Page.stopScreencast is never sent (size never returns to 0), every frame and trace event is JSON.stringified and pushed into ws.send on a CLOSED socket (ws drops it silently when no callback is given), and combined with the handler accumulation in session.ts this grows unbounded over a session.

**Fix.** Register socket.on('close') (and 'error') first, setting a `closed` flag; after the awaits, if closed, immediately call stop()/offTrace(). Also check socket.readyState === OPEN before each send.

### 33. Correction is non-atomic and hand-back failures leave the UI and worker stuck on human control

**Claim.** correction() saves the bumped skill before calling driver.set_control and before saving the run; if set_control fails the skill is left at version+1 with a history entry while the run remains awaiting_human, a retry bumps again, and on the web side any failure in handBack leaves `human` true with no error shown.

**Scenario.** Human clicks Hand back. RunView.tsx:52 stops the recorder (events drained), then api.correction. In api.py the skill is mutated and saved (lines 156-167, version += 1), then line 177 `await driver.set_control(session_id, 'agent')` raises (worker restarted so get() relaunches and times out, or worker down, or a stale session). FastAPI returns 500: skills/<id>.json is already at v+1 with a correction entry, runs/<id>.json is still awaiting_human at the old version, the worker (if up) is still control=human with the recorder stopped. In RunView the rejection escapes the onClick handler, setHuman(false)/setNote('') never run and no message is rendered; the user sees the same panel and clicks again -> the skill goes to v+2 with a duplicate history entry and the same trace re-merged. A related stuck-on-human path: in the graph's handoff node, if POST /control human fails after setControl but inside recorder.start() (server.ts:60, e.g. snapshot during navigation), _drive marks the run failed (api.py:103-109) while the worker is left on control=human with no UI path to reset it (Take over/Hand back are hidden for failed runs).

**Fix.** Order correction as: set_control(agent) first (fail fast, nothing mutated), then mutate+save skill and run together, then schedule _drive; make the step idempotent (e.g. reject a second correction for the same handed-off record). In server.ts /control, roll control back to its previous value if recorder.start() throws. In RunView, wrap handBack/takeOver in try/catch, show the error, and re-enable the button.

### 34. Canvas mouse handlers dereference the image ref before the first frame when humanControl is true

**Claim.** pos() does img.current!.getBoundingClientRect(), but the <img> is only rendered once a frame has arrived; with humanControl true the mouse handlers run over the placeholder div and throw.

**Scenario.** DemoRecorder renders <CoBrowseCanvas humanControl ... /> (DemoRecorder.tsx:75) immediately after /record/start, before the first screencast frame arrives (or during a WS reconnect). The user moves the pointer over 'Waiting for frames from the browser worker…'. onMouseMove -> mouse('mouseMoved') -> pos(e) -> `null.getBoundingClientRect()` -> TypeError thrown from a React event handler on every mouse move; in Next dev this raises the error overlay, in prod it logs uncaught errors. **Fix.** Return early in mouse() when !img.current || !meta (no frame yet), or attach the mouse handlers to the <img> element itself.
